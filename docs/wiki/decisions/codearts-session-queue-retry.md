# CodeArts 会话排队重试与并发闸门

## 背景（现状与约束）

码道按账号限制 3 个并发会话，会话在其请求结束后仍存活约 60–90 秒并计入上限。
超出的聊天请求立即返回 HTTP 400 `TM.00001041`（并发会话数已达上限）。修复前插件
每次请求用随机 `Chat-Id`、每个 loader 用随机 `Session-Id` 新开会话，且 `signedFetch`
只处理 401/403，`TM.00001041` 原样透传给调用方——任何正常调用频率都会饱和上限后
全部失败。

约束：

- magpie 的 `maxConcurrency` 限制的是在途请求数，不是服务端仍在计数的会话数，
  单靠它无法解决（issue #1 已核实）。
- 插件 `fetch` 只能返回 `Response`；调用方（AI SDK / agent）靠 `init.signal` 放弃请求。
- 上游把排队错误同时用两种形态下发：HTTP 400 报文，以及 HTTP 200 + SSE 内嵌
  `error_code`。

## 备选方案

1. **指数退避重试**（5s / 10s / 20s，issue 建议）：实现简单，但单次等待总量与上游
   会话释放时刻无关，短退避窗口（35 秒）不足以跨过 60–90 秒的会话存活期。
2. **只做账号级并发闸门**：把在途请求压到 3 以下，能显著降低触发概率；但会话存活期
   内前一轮请求已占用配额，串行请求间隔小于存活期时仍会撞上限。
3. **排队状态端点轮询 + 固定间隔直接重试**：每次重试前查 `api/v1/queue/status`，
   终态立即失败，其余情况等 10 秒重试整个请求，上限 180 次（约 30 分钟）。
   与参考实现 `Ebony-Vinyl/dsh-our-free-model` 的 CodeArts 通道一致，该实现有真实
   线上使用记录。
4. **在排队期间向用户输出排队位置**：magpie 的插件 `fetch` 只返回最终 `Response`，
   没有独立的瞬态状态通道；提前产出内容会被组装进助手消息并持久化。

## 决策（选定方案）

方案 2 与方案 3 同时实施，并配套稳定会话 id：

- 账号级并发闸门：同账号在途请求不超过 3，超出的排队等待。
- `TM.00001041`（400）不返回调用方，改为每 10 秒重试同一请求，上限 180 次。
- 每次重试前查 `queue/status`：`queue_full` / `error` 立即结束并交回上游原话；
  `waiting` / `working` / 端点不可达则继续等待。
- 非 `TM.00001041` 的 4xx 也先探测一次状态端点，命中 `waiting` 才按排队处理。
- 登录时生成一次 `session_id` 并随凭据持久化，`Session-Id` / `Chat-Id` 由它派生，
  续期沿用旧值；老凭据回退到 `user_id` → `user_name` → `access_key_id`。
- 等待期间 `AbortSignal` 中止立即停止并抛出中止原因。
- 三个参数可由插件选项覆盖：`maxInflight`、`queueRetryDelayMs`、`queueMaxAttempts`。

## 理由（决策依据）

- 上游有显式队列与状态端点，固定间隔轮询能拿到终态，比盲目指数退避更可控；
  10 秒间隔与 180 次上限直接对齐经过线上验证的参考实现。
- 方案 1 的退避窗口短于会话存活期（60–90 秒），单独使用会让重试在配额释放前耗尽。
- 方案 4 与 magpie 插件契约冲突，只能静默等待。
- 稳定会话 id 不依赖上游是否返回身份字段：登录时生成并随凭据持久化，
  `refreshCredential` 显式保留，规避续期轮换 AK 导致的 id 漂移。

## 后果（影响与后续）

- 上游配额满时，请求会长时间挂起（最长约 30 分钟）且无中间输出，调用方需靠
  `AbortSignal` 取消；UI 侧的等待反馈由 magpie 的「运行中」状态承担。
- 排队重试期间占用并发闸门许可，吞吐下降换取不撞上限。
- 未覆盖：HTTP 200 + SSE 内嵌 `error_code`（如 `InferHub.ModelArts.81111.429`）。
  插件只改写响应头而透传正文流，不解析流内事件，该通道的排队错误仍交给上游 AI SDK。
- 真实链路未在本机验证：本仓库无可用华为云凭据，单测用注入 `fetch` 覆盖报文形态；
  需要在真实账号上复测后才能确认线上行为（见 issue #1 的复现脚本）。
